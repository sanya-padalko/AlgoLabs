# Лабораторная работа №7: Эффективные решения задач RMQ и RSQ

## RSQ: Дерево отрезков vs Дерево Фенвика

В этой части сравнивались Дерево Отрезков и Дерево Фенвика, каждое из которых поддерживало запрос суммы на отрезке и изменение значения в точке.

### Результаты тестирования

| Тип дерева | Среднее затраченное время на $10^6$ операций (мс) | Относительное ускорение |
| :---: | :---: | :---: |
| **Дерево Фенвика** | 30.44 | **1.00x** |
| **Дерево Отрезков** | 308.15 | **~10.1x** |

### Вывод по RSQ 
1. **Дерево Фенвика намного быстрее**: В данной части Дерево Фенвика оказалось быстрее Дерева Отрезков более чем в 10.1 раз.
2. **Причины разницы в скорости**:
   * **Обход нужных отрезков**: Переходы между узлами в Дереве Фенвика выполняются с помощью побитовых операций (`i & -i`), которые работают очень быстро, в то время как Дерево Отрезков требует большего количества арифметических действий, вызова рекурсии и проверок условий.
   * **Экономия памяти**: Дерево Фенвика занимает ровно $n + 1$ элемент памяти. Дереву Отрезков требуется массив размером от $2n$ до $4n$ (это несложно доказать, если рассмотреть ближайшую степень двойки большую $n$). Меньше объем памяти - лучше работа кэша.

> **Итоговый вывод по части RSQ**: Для задач вида RSQ, при возможности, стоит отдавать предпочтение Дереву Фенвика, так как оно проще по написанию и своей структуре, менее затратно по памяти и более эффективно по времени.

## RMQ: Различные варианты Sparse Table

Во второй части сравнивались различные расположения индексов в двумерном массиве `st[i][j]` (подразумевается массив Sparse Table).

### Результаты тестирования

| Тип Sparse Table | Среднее затраченное время на $10^6$ операций (мс) | Относительное ускорение |
| :---: | :---: | :---: |
| **`st[n][log_n]`** ($N$ строк) | 49.22 | **~2.1x** |
| **`st[log_n][n]`** (логарифм строк) | 23.19 | **1.00x** |

### Вывод по RMQ
1. **Второй вариант быстрее**: Изменение порядка индексов дало ускорение более чем в 2.1 раза.
2. **Причины**:
   * Поскольку многомерные массивы располагаются в памяти построчно, то при обращении к `st[log_len][lt]` соседние по индексу элементы (`lt`, `lt + 1`, `lt + 2`, ... ,`rt`) лежат в памяти строго друг за другом, что благоприятно для кэша. 
   * В реализации `st[lt][log_len]` изменение индекса `lt` заставляет процессор совершать большие «прыжки» по памяти на величину `MAX_LEVEL`, что приводит к постоянным промахам кэша.

> **Итоговый вывод по части RMQ**: При использовании Sparse Table стоит в качестве первого индекса выбирать номер уровня, тем самым обеспечивая последовательный доступ к памяти и, как следствие, повышая эффективность.
